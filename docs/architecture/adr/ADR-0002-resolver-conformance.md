# ADR-0002: One authoritative matching core with cross-runtime conformance vectors

Status: **Proposed** (implemented + locally verified on `refactor/openva-resolver-unification`; not deployed; not live-accepted).
Work package: WP-OPENVA-RESOLVER-UNIFICATION-01.

## Context
Vendor identity resolution is implemented on several transports: the Python core
`openva_vendor_inventory_matcher.core` (owns the `0.90` confidence threshold, the `0.05`
ambiguity margin, domain/name normalization, legal-suffix stripping, registration-number
matching, and the `matched`/`no_match`/`ambiguous` status vocabulary), the CSV adapter and MCP
surfaces that already import that core, and the browser (`site/app.js`) plus Cloudflare Worker
(`worker/worker.js`) which each carry their own hand-written `normalizeDomain`. Nothing pins the
transports to identical outcomes, so a normalization or threshold change in one runtime could
silently diverge — a governance and provenance risk (a public source could be attributed to the
wrong vendor, or a fail-closed ambiguity could be resolved differently per transport).

## Decision
Treat `openva_vendor_inventory_matcher.core` as the single authority and freeze its externally
observable behaviour as a committed conformance suite,
`tests/conformance/resolver-conformance.json`, generated by `tools/openva/resolver_conformance.py`.
The suite emits:

- a **contract** — thresholds, per-method confidences, the status vocabulary, and the legal-suffix
  set — read directly from the core, so no transport hand-maintains its own copy of `0.90`; and
- **conformance vectors** whose expected outcomes are *computed by running the core* over a small
  deterministic fixture catalog, covering every required case class: exact domain (incl.
  scheme/path/`www` stripping), subdomain, shared-parent-domain ambiguity, exact name,
  stripped-legal-suffix name, name ambiguity, no-match, malformed input, internationalized domain,
  conflicting identity (domain wins over a weaker name; and the registration-vendor-conflict
  fail-closed path where neither vendor is attributed), and registration-number matching
  (exact and ambiguous).

`check` **fails closed** if the core stops reproducing any committed vector, if a contract
constant drifts, if a declared legal suffix is no longer stripped, or if the committed artifact
is stale. It is wired into `tools.openva.validate.validate_all` as `check_resolver_conformance`.

## Consequences
- Additive and backward-compatible: no matching behaviour changes; the artifact asserts the
  current core behaviour and locks it against silent regression.
- A later increment ships a JS conformance harness that runs the browser and Worker resolvers
  against this same artifact, proving cross-runtime parity before any consolidation of the
  duplicate `normalizeDomain` implementations. This ADR deliberately does **not** yet remove those
  duplicates — the lock is the prerequisite, not the removal.
- The fixture catalog is intentionally tiny and self-contained (no dependency on the live
  canonical catalog), so the vectors are deterministic and reviewable.

## Alternatives considered
- Hand-write expected outcomes in the test: rejected — expectations that are not computed from the
  core drift from it and become a second source of truth. Computing them from the core keeps the
  core authoritative while still failing closed on behaviour change (via the staleness + vector
  reproduction checks).
- Consolidate the browser/Worker normalizers immediately: rejected for this increment — higher
  blast radius on the live resolver boundary; the conformance lock delivers the core value (a
  provable single authority) at far lower risk and is the safe precondition for consolidation.
