# Agent Export Contract

OpenVA publishes static, deterministic, versioned JSON exports so AI agents can locate vendor assurance sources, understand confidence and retrieval method, and check the latest observed health and freshness — without scraping README files, docs, or internal repository YAML.

OpenVA does not version vendor truth. OpenVA observes vendor-published sources and records source state, provenance, hashes, timestamps, and change signals. An export describes the state of public source references; it never means OpenVA approves, recommends, certifies, scores, or determines whether any vendor is compliant, safe, adequate, suitable, low risk, or high risk.

## Static exports vs live resolution

These agent exports are **static, deterministic snapshots** of the catalogue. For
a live, resolve-on-use result — where an agent supplies a vendor plus the required
source types and OpenVA verifies catalogue links during the request, discovers
replacements for stale or broken sources, and routes discoveries into the
catalogue lifecycle — use the unified resolution contract
(`resolve_vendor_sources`) documented in `docs/vendor-resolution.md`. The live
response distinguishes a catalogue-derived result from a live-discovery result
(`origin`), a cached observation from a current live check (`live_checked`,
`checked_at`), and a pending catalogue update from a canonical record
(`catalog_status`), and it carries the same `snapshot` identity (`commit_sha`,
`generated_at`) as these exports.

OpenVA preserves source-reference and observation history. It does not archive or
reproduce historical vendor documents.

## Where the exports live

Exports are publish-time artifacts generated by `site-pages.yml` and served by the OpenVA site under:

```text
<site-base-url>/public/openva-agent-index.json
<site-base-url>/public/vendors/index.json
<site-base-url>/public/vendors/{vendor_id}.json
<site-base-url>/public/sources/index.json
<site-base-url>/public/observations/latest.json
<site-base-url>/public/changes/latest.json
```

They are NOT committed to the repository. Start at `openva-agent-index.json`: it lists every other export with its path and content digest.

A human- and crawler-facing discovery surface wraps these exports on the same site: one static page per vendor at `/vendors/{vendor_id}/`, an integration guide at `/agents/`, and a typed manifest at `/.well-known/openva.json` whose `agent_index_url` points back to `openva-agent-index.json`. Each vendor page links to that vendor's JSON export and preserves the original vendor-published source URLs. The canonical base URL and these OpenVA-owned paths derive from `config/publication.yaml`.

## Snapshot identity

Every export carries:

```json
"snapshot": {
  "commit_sha": "<repository commit the export was generated from>",
  "generated_at": "<build time, ISO 8601>",
  "digest": "sha256:<hex>"
}
```

The export contract is versioned by `schema_version` (`0.1.0`) plus snapshot commit/digest — never by a catalog-wide semantic version.

**Digest verification recipe:** remove the `snapshot` block from the document, serialize the remainder as canonical JSON (UTF-8, sorted keys, separators `","`/`":"`, no trailing newline), and compute `sha256:` over those bytes. The result must equal `snapshot.digest`. The root index's `exports` and `vendor_exports` maps list the digests of every other file; the map excludes the root index itself, and the root index's own digest is computed over its payload excluding its own snapshot block — no digest ever covers an object containing that digest.

## Per-vendor export shape

```json
{
  "schema_version": "0.1.0",
  "snapshot": { "commit_sha": "...", "generated_at": "...", "digest": "sha256:..." },
  "vendor_id": "github",
  "canonical_name": "GitHub",
  "domains": ["github.com"],
  "sources": [
    {
      "source_id": "github-subprocessors",
      "source_type": "subprocessors_list",
      "source_url": "https://...",
      "canonical_confidence": "canonical",
      "retrieval_method": "html_page",
      "machine_readable": false,
      "source_health": "reachable",
      "last_observed_at": "2026-06-12T05:30:00Z",
      "material_change_since_baseline": false
    }
  ],
  "not_advice": true
}
```

Field semantics:

- `canonical_confidence`, `retrieval_method`, `machine_readable` come from the reviewed source record (null when the optional registry fields are not yet adopted on that record).
- `source_health` carries the latest available observed-health vocabulary: `reachable | unreachable | gated | bot_protected | redirected | quarantined`. **Null means not yet observed**, not unhealthy.
- `last_observed_at` is the latest observation timestamp for the source, or null.
- `material_change_since_baseline` compares the latest observed normalized sample hash against the source record's curated change-detection baseline; null when either side is missing.

## Observation inputs and honest degradation

Health, last-observed, and freshness data come from the latest source-maintenance run artifact when available. The `observation_input` field (on the agent index and observations export) records which input class built the export:

```text
run_artifact               latest-observations + freshness reports from the newest maintenance run
committed_events_fallback  the committed change-event ledger (SPARSE: events only, so health may lag
                           a no-change re-observation); used only when the run artifact is unavailable
none                       no observation input was available; observed fields are null
```

`changes/latest.json` always derives from the committed change-event ledger (latest event per source) — that is its correct source. `observations/latest.json` rows include per-source `freshness` (fresh | stale | expired | unknown vs the observation SLA) when the freshness report is available.

## What the exports never contain

- No embedded API or server — the exports themselves are static, digest-verifiable files. They can be read directly, or served read-only by the separate MCP server over stdio or Streamable HTTP (`integrations/mcp/openva_mcp`); OpenVA operates no production hosted endpoint.
- No private or gated document contents: URLs, enums, timestamps, and hashes only.
- No legal conclusions and no vendor risk scores.
- No full observation history by default — latest state only; durable history lives in the committed change-event ledger.
- No advisory wording: nothing in an export means approved, recommended, compliant, suitable, safe, or any risk level.

## Determinism

The builder is a pure function of (catalog records, committed event ledger, optional run-artifact inputs) with `commit_sha`/`generated_at` injected. Identical inputs produce byte-identical export trees and identical digests; ordering is sorted by `vendor_id`/`source_id` throughout. This is enforced by build-twice tests in CI.
